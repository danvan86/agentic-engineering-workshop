Agentic Engineering

denktKI
entscheidetMensch
taugt fürProduktivcode

Der Agent arbeitet selbstständig, innerhalb von Regeln, Spec und Prüfungen, die du festlegst.

Agentic Engineering heißt: den Handlungsspielraum des Agenten eingrenzen und ihn Schritt für Schritt führen.

Dafür braucht es zuerst ein Bild davon, wie ein Agent arbeitet.

Wie Agenten arbeiten

Der ReAct-Zyklus

Wie Agenten arbeiten

Das Kontextfenster verbraucht sich im Lauf einer Sitzung.

Die Kernursache

Fehlt eine Information, füllt der Agent die Lücke selbst.

Erwartung

„Er wird schon fragen, wenn etwas unklar ist."

Verhalten

Die Lücke wird mit der wahrscheinlichsten Annahme gefüllt. Lautlos, ohne Hinweis.

Folge

Die meisten Fehlschläge sind geratene Annahmen.

Deshalb steht in fast jedem Prompt dieser Sammlung dieselbe Zeile: Rate nichts. Frag mich.

Stochastik

Gleicher Prompt, gleiches Repo, drei Ergebnisse.

Die Frage, die zwei Tage an der Wand hängt

Wie macht man Arbeit mit einem stochastischen Werkzeug verlässlich?

Nach jedem Block kommt eine Antwort dazu.

Die Antwort in einem Bild

Fünf Dinge grenzen den Spielraum ein.

Die Arbeitskette

Pro Feature derselbe Weg.

Wo die Dateien liegen

Ein Ordner pro Feature.

mein-projekt/
├── CLAUDE.md          Regeln, Konventionen
├── ARCHITECTURE.md    Gesamtbild des Systems
├── features.md        Tag 1: Liste der Features
├── .claude/
│   ├── settings.json  Hooks
│   └── skills/        Projekt-Skills
└── specs/
    ├── open/
    │   └── csv-export/
    │       ├── brainstorming.md
    │       ├── spec.md
    │       └── progress.md
    └── done/          abgeschlossene Features
  • Der Agent bekommt einen Pfad und hat alles zu diesem Feature.
  • done/ hält Abgeschlossenes aus dem Blickfeld. In der CLAUDE.md steht, dass dieser Ordner nur auf Nachfrage gelesen wird.
  • An Tag 2 heißt der Ordner nach dem Ticket, etwa PROJ-123-csv-export/. Der Ticket-Text steht als Ausgangslage oben in der brainstorming.md.
  • ARCHITECTURE.md liegt im Wurzelverzeichnis und wird im Abschluss jedes Features geprüft.

Schritt 1 · features.md

Die Idee schildern, der Agent leitet die Features ab.

Auch die Features, die in der Idee stecken, ohne dass man sie ausdrücklich genannt hat: Anmeldung, Datenhaltung, Export, Fehlerfälle.

features.md ist die gemeinsame Referenz, bis zu jedem Feature eine Spec existiert. Danach kann sie gelöscht werden. An Tag 2 übernimmt das Ticket diese Rolle.

Prompt 01 
Hier ist meine Projektidee:
{{Beschreibung, so ausführlich wie möglich}}

Leite daraus die Features ab, die diese Idee
voraussetzt, auch die, die ich nicht ausdrücklich
genannt habe. Schreib sie in eine features.md:

- pro Feature ein Satz, was es kann
- Reihenfolge: was zuerst da sein muss
- was für eine erste lauffähige Version
  wegfallen kann

Stell mir zuerst die Fragen, die du dafür
brauchst. Noch keine Spec, noch kein Code.

Schritt 2 · CLAUDE.md

Was in jeder Sitzung gilt, steht in einer Datei.

Sprache, Struktur, Konventionen, Testframework, verbotene Wege. Alles, was der Agent sonst in jeder neuen Sitzung von vorn erraten müsste.

Andere Agenten-Werkzeuge nutzen dafür eine AGENTS.md. Inhalt und Zweck sind dieselben.

Prompt 02 
Lass uns eine CLAUDE.md erstellen, die festhält,
was du beim Arbeiten in diesem Projekt jedes Mal
wissen musst. Grundlage ist die features.md.

Schlag mir vor:
- Sprache, Framework, Testframework,
  wie man startet und testet
- Ordnerstruktur, inklusive specs/open/ und
  specs/done/ (done/ nur auf Nachfrage lesen)
- Namenskonventionen und Fehlerbehandlung
- Was nie getan werden soll

Frag mich, bevor du etwas festschreibst.
Kurze Anweisungen, keine Prosa.

Schritt 3 · brainstorming.md

Brainstorming in mehreren Runden

Der Agent schlägt eine Lösung vor, der Mensch wählt aus und beantwortet die Fragen direkt in der Datei. Danach passt der Agent Optionen und Empfehlung an.

Prompt 03 
Wir bereiten dieses Feature vor:
{{Feature-Beschreibung oder Ticket-Text}}

Schreib specs/open/{{feature}}/brainstorming.md mit
- Ausgangslage (die Beschreibung von oben)
- Lösungsoptionen mit Vor- und Nachteilen
- deiner Empfehlung mit Begründung
- Risiken
- offenen Fragen an mich

Wir gehen das in mehreren Runden durch: Ich
markiere meine Auswahl und beantworte die Fragen
in der Datei, du passt daraufhin Optionen und
Empfehlung an. Bis keine Frage mehr offen ist.

Noch keine Spec, noch kein Code.

Schritt 4 · spec.md

Anatomie einer Spec

Offene Fragen gehören nicht in die Spec. Sie werden im Brainstorming geklärt. Erst wenn dort keine mehr offen ist, entsteht die Spec.

Prompt 04 
Prüfe zuerst, ob in brainstorming.md noch Fragen
offen sind. Wenn ja: nenne sie und hör auf.

Sonst erzeuge spec.md im selben Ordner:
- Intent: Warum gibt es das?
- Scope: Was ist enthalten?
- Non-Goals: Was ausdrücklich nicht?
- Akzeptanzkriterien: nummeriert, einzeln
  überprüfbar, als beobachtbares Verhalten
- Constraints: technische und fachliche Grenzen

Beschreibe das Was und Warum, nie das Wie.
Wenn ein Akzeptanzkriterium nicht objektiv
überprüfbar ist, schreib es um.

Noch kein Code.

Schritt 5 · Skills ableiten

Der Agent liest das Vorgehen aus deinen eigenen Dateien.

Der Skill beginnt beim Brainstorming. Was davor kommt, ist austauschbar: an Tag 1 ein Eintrag aus der features.md, an Tag 2 ein Ticket.

Prompt 05 
Wir sind für Feature {{feature}} diesen Weg
gegangen: brainstorming.md in mehreren Runden,
danach spec.md.

Lies beide Dateien und rekonstruiere daraus das
Vorgehen: welche Schritte, welche Rückfragen an
mich, welche Struktur im Ergebnis.

Leg daraus einen Skill unter
.claude/skills/{{name}}/SKILL.md an. Eingabe des
Skills ist eine Feature-Beschreibung, egal ob aus
der features.md oder aus einem Ticket.

Stütz dich auf die Dateien, nicht auf dein
Gedächtnis an unsere Unterhaltung.

Schritt 6 · Umsetzung

Erst der Plan in progress.md, dann der Code.

spec.md bleibt unverändert und ist der Maßstab im Review. progress.md ändert sich laufend. Wer den Plan vor dem ersten Code lesen will, startet im Plan Mode.

Prompt 06 
Setze specs/open/{{feature}}/spec.md um.

Schreib zuerst einen Plan als Checkliste in
progress.md:
- Schritte in Reihenfolge
- zu jedem Schritt das Akzeptanzkriterium,
  das er erfüllt, und wie er getestet wird
- Abschnitte "Entscheidungen", "Offene Punkte"
  und "Review"

Dann arbeite die Checkliste ab. Nach jedem
Schritt: Tests laufen lassen, abhaken,
Entscheidungen notieren.

Fehlt dir etwas: nicht raten. Unter
"Offene Punkte" notieren und mich fragen.

Schritt 7 · Review

Review in einer neuen Sitzung, in drei Stufen.

Die neue Sitzung ist Absicht: Der Agent, der den Code geschrieben hat, prüft gegen sein eigenes Verständnis. Ein frischer Agent prüft gegen die Spec.

Prompt 07 · in einer neuen Sitzung 
Prüfe specs/open/{{feature}}/ gegen die
spec.md. Du hast den Code nicht geschrieben.

1. Lass die Tests laufen. Schlagen sie fehl,
   brich ab und melde nur das.
2. Geh jedes Akzeptanzkriterium durch: Ist es
   erfüllt, und woran erkennst du das? Was du
   nicht nachweisen kannst, ist ein Befund.
   Wurde etwas gebaut, das nicht in der Spec
   steht, oder ein Non-Goal verletzt?
3. Prüfe gegen SOLID und DRY. Melde nur
   konkrete Verstöße mit Begründung.

Schreib die Befunde als Checkliste unter
"Review" in progress.md. Ändere noch nichts.

Warum ein frischer Agent prüft

Ein grüner Test, der am Kriterium vorbeiprüft.

Schritt 8 · Befunde beheben

Beheben, abhaken, erneut prüfen.

Einzelne kleine Befunde lassen sich auch direkt beheben. Bei mehreren sorgt die Liste dafür, dass nichts verloren geht, wenn die Sitzung endet.

Prompt 08 
Arbeite die Befunde unter "Review" in
specs/open/{{feature}}/progress.md ab.

- Einen Befund nach dem anderen.
- Nach jedem: Tests laufen lassen, Befund
  abhaken.
- Lässt sich ein Befund nur beheben, indem die
  Spec verletzt wird: nicht raten, mich fragen.

Wenn alle abgehakt sind: sag Bescheid, dann
läuft das Review erneut.

Schritt 9 · Abschluss

Was sich wiederholen würde, wird zur Regel.

  • ARCHITECTURE.md prüfen und nachziehen, wo das Feature etwas verändert hat
  • PR-Beschreibung aus spec.md und progress.md
  • Ordner von specs/open/ nach specs/done/
  • Erkenntnisse zurückführen: in die CLAUDE.md, einen Skill oder einen Hook

Ein Befund, der als Linter-Regel endet, taucht im nächsten Review nicht mehr auf.

Prompt 09 · Prompt 10 für 01–03 im Reiter „Prompts" 
Lies die Review-Befunde in
specs/open/{{feature}}/progress.md.

Welche davon würden bei einem anderen Feature
wieder auftreten?

Schlag mir für jeden vor, wo er künftig
abgefangen wird:
- als Regel in der CLAUDE.md
- als Schritt in einem Skill
- als Prüfung in Linter oder Hook

Ändere noch nichts.

Tag 2 · Verstehen

ARCHITECTURE.md: das Gesamtbild des Systems.

Der Agent liefert einen Entwurf. Bevor er ins Repo kommt, prüft ihn jemand, der das System kennt. Jede spätere Sitzung baut auf dieser Datei auf und übernimmt damit auch ihre Fehler.

Prompt 11 · für jedes Repo, auch das von gestern 
Erkunde dieses Repository und schreibe
ARCHITECTURE.md:

- Überblick: Was macht das System, für wen?
- Module und ihre Verantwortlichkeit
- Datenflüsse: wo kommen Daten rein, wo raus
- Technologien: Sprachen, Frameworks,
  Datenbanken, Infrastruktur

  Entwurfsmuster wo verwendet werden

  Umgang mit Secrets und Eingaben

Erzeuge für die Module zusätzlich ein
Mermaid-Diagramm.

Tag 2 · Absichern

Vor der Umsetzung zwei Fragen.

Frage 1

Was ist betroffen?

Alle Stellen, die den zu ändernden Code aufrufen oder von ihm abhängen.

Frage 2

Ist es abgesichert?

Abgesichert wird nur, was die Änderung berührt. Oft reicht ein Test auf Ebene der Schnittstelle, der den betroffenen Ablauf einmal durchspielt.

Prompt 14 
Lies spec.md in specs/open/{{feature}}/,
die CLAUDE.md und die ARCHITECTURE.md.

Bevor wir umsetzen, klär zwei Fragen:
1. Was ist betroffen? Alle Stellen, die den
   zu ändernden Code aufrufen oder von ihm
   abhängen.
2. Ist es abgesichert? Welche dieser Stellen
   sind durch Tests abgedeckt?

Wo Tests fehlen: Schlag mir die kleinste
Absicherung vor, die den betroffenen Ablauf
abdeckt, etwa einen Test auf Ebene der
Schnittstelle statt vieler Unit-Tests.

Ergebnis in progress.md unter "Vorab".
Noch kein Code.

Ausblick · Hooks

Hooks halten den Agenten technisch in der Spur.

Anweisungen in CLAUDE.md und Spec befolgt der Agent mit hoher Wahrscheinlichkeit. Ein Hook ist ein Programm, das bei jedem Mal läuft.

Ausblick · zwei Beispiele

Beides steht in .claude/settings.json.

{
  "permissions": {
    "deny": ["Read(./.env)", "Edit(./.env)"]
  },
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
      }]
    }]
  }
}
Beispiel 1 · .env sperren

Dafür braucht es keinen Hook. Eine deny-Regel verbietet den Dateiwerkzeugen von Claude Code, die Datei zu lesen oder zu bearbeiten.

Beispiel 2 · Formatter nach jeder Änderung

Nach jedem Bearbeiten oder Schreiben einer Datei übergibt Claude Code dem Befehl, welche Datei es war. jq liest den Pfad aus, prettier formatiert genau diese Datei.

How agents work

The root cause

When information is missing, the agent fills the gap itself.

Expectation

Behaviour

The gap is filled with the most likely assumption. Silently, without a hint.

Most failures are guessed assumptions.

Where the files live

One folder per feature.

my-project/
├── CLAUDE.md          rules, conventions
├── ARCHITECTURE.md    big picture of the system
├── features.md        day 1: list of features
├── .claude/
│   ├── settings.json  hooks
│   └── skills/        project skills
└── specs/
    ├── open/
    │   └── csv-export/
    │       ├── brainstorming.md
    │       ├── spec.md
    │       └── progress.md
    └── done/          finished features
  • The agent gets one path and has everything about this feature.
  • done/ keeps finished work out of sight. CLAUDE.md says this folder is only read on request.
  • On day 2 the folder is named after the ticket, e.g. PROJ-123-csv-export/. The ticket text goes at the top of brainstorming.md as the starting point.
  • ARCHITECTURE.md sits in the root directory and is checked when each feature is wrapped up.

Step 4 · spec.md

Anatomy of a spec

Open questions don't belong in the spec. They are settled during brainstorming. The spec is only written once nothing is left open there.

Prompt 04 
First check whether any questions are still

- Intent: why does this exist?
- Scope: what is included?
- Non-goals: what explicitly not?

Step 7 · review

Review in a new session, in three stages.

The new session is deliberate: the agent that wrote the code checks against its own understanding. A fresh agent checks against the spec.

Prompt 07 · in a new session 
Check specs/open/{{feature}}/ against
spec.md. You did not write the code.

1. Run the tests. If they fail, stop and
   report only that.
2. Go through every acceptance criterion: is it
   met, and how can you tell? Anything you
   can't demonstrate is a finding.
   Was anything built that isn't in the spec,
   or was a non-goal violated?
3. Check against SOLID and DRY. Report only
   concrete violations, with reasoning.

Write the findings as a checklist under
"Review" in progress.md. Don't change anything yet.

Why a fresh agent checks

A green test that misses the criterion.

Step 8 · fixing findings

Fix, tick off, check again.

Single small findings can also be fixed right away. With several, the list makes sure nothing gets lost when the session ends.

Prompt 08

- After each one: run the tests, tick it off.
- If a finding can only be fixed by violating
  the spec: don't guess, ask me.

When everything is ticked off: let me know,
then the review runs again.

Outlook · hooks

Hooks keep the agent on track technically.

The agent follows instructions in CLAUDE.md and the spec with high probability. A hook is a program that runs every single time.

Outlook · two examples

Both live in .claude/settings.json.

{
  "permissions": {
    "deny": ["Read(./.env)", "Edit(./.env)"]
  },
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
      }]
    }]
  }
}
Example 1 · locking .env

No hook needed. A deny rule forbids Claude Code's file tools from reading or editing the file.

Example 2 · formatter after every change

After every edit or write, Claude Code tells the command which file it was. jq reads the path, prettier formats exactly that file.
